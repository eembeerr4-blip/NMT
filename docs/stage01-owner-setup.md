# Этап 01: настройки владельца и подготовка рабочей базы

Реализация пока находится в отдельной ветке `codex/stage01-auth`. Рабочий сайт на `localhost:3000` и его `prisma/dev.db` не обновлялись.

## Почта

Приложение отправляет письма через Resend API. Создайте аккаунт у провайдера, подтвердите собственный домен отправителя и задайте в локальных секретах окружения:

- `RESEND_API_KEY` — секретный API-ключ;
- `AUTH_EMAIL_FROM` — подтверждённый адрес отправителя;
- `AUTH_BASE_URL` — точный публичный HTTPS-адрес сайта без пути.

Не записывайте значения в Git. Для проверки настоящей доставки нужны работающий домен отправителя и доступная почта получателя. Пока они не настроены, email-регистрация показывает недоступность и приглашение не расходуется. Существующие пользователи могут входить по никнейму.

## Google

В Google Cloud создайте OAuth consent screen и OAuth Client типа **Web application**. Для локальной QA-среды разрешённый redirect URI должен точно совпадать с адресом приложения, например `http://127.0.0.1:3101/api/auth/google/callback`. Для будущего публичного сайта добавьте `https://ВАШ-ДОМЕН/api/auth/google/callback`. Укажите разрешённых тестовых пользователей, если consent screen остаётся в режиме тестирования.

Задайте `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` и тот же `AUTH_BASE_URL`. Приложение проверяет подпись Google ID token, issuer, audience, срок действия, nonce и `email_verified`; личность связывается по стабильному Google `sub`. Совпадение email само по себе **не** привязывает Google к существующему профилю. Владелец существующего профиля инициирует привязку из своих настроек после входа.

## Закрытая регистрация

После развёртывания владелец создаёт индивидуальный код на странице `/admin/invitations` (ссылка также есть в «Користувачі та ролі»). Код привязан к одному email, действует семь дней и используется один раз. Он нужен и для регистрации с паролем, и для создания нового аккаунта через Google. Приглашения и токены восстановления хранятся только как SHA-256-хеши. Код показывается владельцу после создания — сохраните и передайте его адресату самостоятельно.

Старый профиль без email может добавить адрес через «Налаштування» и подтвердить ссылкой из письма. До подтверждения старый способ входа остаётся доступен, а сброс пароля для этого адреса не включается.

## Рабочая SQLite: отдельное согласование

На рабочей базе сейчас применены 4 миграции. В ветке этапа 01 — 8 миграций: прежняя `20261018130000_nickname_case_insensitive` и три новые (`closed_auth`, `email_nocase`, `account_email_link`) ещё не применены к рабочей базе. Никаких команд ниже на ней пока не выполнялось.

Перед отдельным разрешением на развёртывание: остановить записи в рабочую базу; сделать свежую SQLite-consistent резервную копию; проверить `integrity_check`, `foreign_key_check`, повторяющиеся никнеймы без учёта регистра, число строк и текущие миграции; проверить применение всей цепочки на **свежей** копии. SQL новых миграций только добавляет nullable-поля, таблицы и индексы, без `DROP` и пересоздания таблиц. После согласованного применения нужно повторить проверки целостности, числа строк и `migrate diff --exit-code`, затем проверить вход старого владельца и сохранность его данных.

QA уже подтвердило эту последовательность на копии базы; это не заменяет повторную проверку непосредственно перед обновлением рабочей базы.

## Проверки и ограничения

Автоматические тесты использовали временную SQLite и локально подписанные тестовые Google-токены. Браузерный сценарий использовал отдельный сервер `127.0.0.1:3101`, вторую QA-копию и локальный почтовый приёмник. Скриншоты находятся в `docs/stage01-qa/`. Настоящий Google OAuth и доставка писем через Resend пока не проверены: для них нужны перечисленные выше настройки.
