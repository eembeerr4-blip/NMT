## NMT Academy: порядок роботи AI-агентів

Ці правила доповнюють блок Next.js вище. Поточний проєкт: D:/НМТ Сайт/NMT-academy. Перед роботою прочитай ARCHITECTURE.md, PLAN.md, поточний код і локальніші AGENTS.md, якщо вони з'являться. Перевір фактичні HEAD, гілку, git status та цільову папку: старі SHA, шляхи й звіти можуть застаріти. Інструкція власника у поточному завданні має пріоритет над загальним шаблоном. Затверджена власником дорожня карта — етапи 00–09 у PLAN.md; A01–A06 можуть бути лише підпланами. Останнє продуктове рішення — відкрита реєстрація без обов'язкового запрошення для email і нового Google-профілю; не повертай вимогу запрошення без нового рішення власника.

### Розподіл відповідальності

Власник затверджує продуктове рішення і дозволяє ризикові операції. ChatGPT виступає архітектором та незалежним рев'юером. Codex/інший виконавець реалізує тільки погоджену задачу, перевіряє факти й надає відтворюваний результат для рев'ю. Не називай заплановане «готовим», а статичний аналіз — перевіркою в браузері.

### Контракт кожної задачі

Перед змінами зафіксуй у завданні або короткому робочому плані:
1. Ціль і очікувана поведінка.
2. Конкретні файли/модулі та дані, які можуть бути зачеплені.
3. Обмеження: що не змінювати; яка база, сервер і worktree дозволені.
4. Критерії готовності, включно з помилками, ролями та мобільним станом, якщо це релевантно.
5. Найменший достатній набір цільових тестів і спосіб перевірки.

Якщо бракує однієї з п'яти частин, виведи її з контексту й коду, познач припущення. Не розширюй область без причини. Коли джерела конфліктують, наведи шляхи, факти та наслідок.

### Безпека даних і Git

- Робоча SQLite — prisma/dev.db; з увімкненим WAL можливі dev.db-wal і dev.db-shm. Не запускати на ній reset, db push, seed, restore, upgrade або migrate без окремого дозволу власника. Не копіювати одну dev.db як «бекап» працюючої бази. Перш ніж торкатися даних, довести шлях DATABASE_URL без виведення секретів і створити узгоджену копію.
- Тести з записом виконувати лише на ізольованій QA SQLite. Прочитати package.json, тестові конфіги й setup перед npm script: назва script не доводить його безпечності. tests/db.test.ts виконує db push; audit-database/plan-upgrade потребують спеціальної disposable-бази. Не направляти весь npm test на робочу БД.
- Захищати на сервері кожну дію й API. Для приватних даних перевіряти userId і роль у всьому ланцюгу. Не замінювати guard прихованою кнопкою. OWNER, ADMIN, EDITOR і STUDENT мають різні дозволи.
- Не друкувати й не включати в звіт/ZIP .env, токени, OAuth secrets, passwordHash, робочу базу або персональні записи. Повний owner JSON-backup містить passwordHash; його не надсилати рев'юеру як звичайний артефакт.
- Зберігати сторонні незакомічені й untracked файли. Не робити reset/clean/stash/rebase/merge/push або коміт без дозволу в задачі. Перед зупинкою процесу визначити PID, команду й каталог; не завершувати чужий сервер.

### Економні перевірки

- Малий текстовий/UI-фікс: адресний тест або браузерний сценарій потрібної сторінки; typecheck/lint лише якщо зміна може їх зачепити. Не запускати повну батарею механічно.
- Зміна дії, авторизації чи даних: цільові unit/integration тести, негативний сценарій, перевірка ролі й власника запису, typecheck. Браузер — коли змінено користувацький шлях.
- Повний lint/test/build/e2e та сценарії різних ролей — після значних змін, міграцій або перед релізом. Перед повним тестом довести ізоляцію БД. Невиконане позначати SKIPPED з причиною, не PASS.
- Повторювати широкий прогін тільки після нової зміни, помилки або невирішеного ризику. Зберігати фактичні команди і короткі результати.
- У Next.js 16 перед редагуванням коду читати релевантні локальні docs із node_modules/next/dist/docs/ відповідно до правила вище.

### Завершення кожної задачі

Створити/оновити TASK-REPORT.md: ціль; що змінено; рішення; змінені, нові й видалені шляхи; що перевірено/не перевірено; команди й результати; HEAD/гілка/status; ризики; дії власника. Вказати межу поточної задачі, не приписувати їй старі зміни.

Створити TASK-CHANGES.zip тільки з нових і змінених файлів цієї задачі зі шляхами від кореня репозиторію. Видалені шляхи перелічити лише в звіті; їхній вміст не архівувати. Не включати весь проєкт, бази, .env, ключі, node_modules, .next, резервні копії, скриншоти з персональними даними чи старі audit-файли. Якщо зміни великі, додати Git diff і перелік SHA комітів у звіт або окремий безпечний документ задачі. Перевірити список ZIP перед передачею. ZIP не вкладати у самого себе.

Зупинятися на межі дозволеного етапу. PLAN.md фіксує затверджену власником дорожню карту 00–09; для етапів 02–09 окремі детальні ТЗ готуються перед виконанням. A01–A06 — лише можливі технічні підплани, підпорядковані затвердженим етапам. Затвердження дорожньої карти не є дозволом автоматично починати наступний етап.
