# NMT Academy — фактическая архитектура

Срез: 21 октября 2026 года, основная ветка cursor/nmt-academy-lessons-and-audit, HEAD 4e02c68ea8accc810dcd9bd5853e4931640ab01b. Это описание кода, а не подтверждение готовности публичного запуска. При расхождении с более старыми README и docs источником истины служат текущий код и schema.prisma; решения владельца о будущем продукте отмечены отдельно.

## Платформа и границы модулей

- Next.js 16.4.2 App Router, React 19.3, TypeScript, Prisma и @prisma/client 6.19.3, SQLite. Версии проверены в package.json. UI использует Tailwind, Radix, lucide-react, Recharts и KaTeX.
- src/app содержит маршруты. Группа (main) — главная, предметы, темы, урок, план, календарь, практика/тесты, результаты, прогресс, заметки и настройки. Отдельно расположены /login, /register, /onboarding, /forgot-password, /reset-password, /verify-email, /editor и /admin. src/app/api содержит Google callback, AI stream и экспорты. Группа в скобках не входит в URL.
- src/components содержит UI и интерактивные сценарии; src/server — серверные действия, сессии, авторизация, синхронизация плана и общие операции; src/lib — правила, расчёты, валидация и Prisma client. Сложные действия сосредоточены в src/server/actions.ts; менять их только узкими задачами с тестами собственности данных.
- src/proxy.ts проверяет наличие session-cookie и возвращает JSON 401 для анонимных API-запросов. Это быстрый фильтр, не авторизация: действительность сессии проверяет src/server/session.ts. Layout группы (main) получает пользователя и вызывает syncPlan; это означает возможную запись в учебные задачи при открытии учебной страницы. Административный и редакторский layout используют серверные guards.
- Конфигурация Next в next.config.ts включает Turbopack CSS и заголовки no-referrer/no-store для ссылок подтверждения email и сброса пароля.

## Данные и миграции

- Источник модели — prisma/schema.prisma: 32 модели. Группы: User/Session и OAuthAccount/AuthToken/Invitation/OAuthFlow; Subject/Topic/VideoLesson/Question/Test; персональные UserSubject/UserTopicProgress/Note/TestAttempt/Answer/ExamResult/StudyTask/ReviewSchedule/Mistake/Flashcard/UserVideoProgress; настройки, AI-история, достижения, XP и AuditLog.
- В prisma/migrations находятся восемь миграций: init, reconcile_history, normalize_user_video_progress, add_query_indexes, nickname_case_insensitive, closed_auth, email_nocase, account_email_link. Наличие миграции в Git само по себе не доказывает её применение на каждой базе.
- DATABASE_URL=file:./dev.db в Prisma относится к каталогу prisma; рабочая база — prisma/dev.db. src/lib/sqlite-init.ts включает WAL и busy_timeout. Копировать только dev.db во время работы сервера нельзя: свежие транзакции могут находиться в -wal. Для резервирования нужна согласованная SQLite online backup и проверка integrity/foreign keys.
- Тесты с записью требуют отдельной SQLite. Часть интеграционных тестов создаёт собственные временные базы; tests/db.test.ts вызывает db push, а tests/audit-database.test.ts и tests/plan-upgrade.test.ts требуют специальную disposable-базу и порядок запуска. Команда npm test не считается безопасной для рабочей базы без проверки этих условий.

## Аккаунты и полномочия

- src/server/session.ts создаёт случайный токен, хранит в Session только его SHA-256 и устанавливает HttpOnly SameSite=Lax cookie. requireUser, requireAdministrator и requireContentEditor выполняют серверную проверку. src/lib/permissions.ts задаёт иерархию OWNER > ADMIN > EDITOR > STUDENT; профиль с id owner фактически OWNER независимо от записанной роли. Полная JSON-копия доступна только владельцу.
- Текущий код допускает публичную регистрацию без приглашения: src/server/auth-service.ts создаёт STUDENT, требует валидные email/никнейм, пароль от 8 до 1024 символов и совпадение подтверждения. Email надо подтвердить до входа. Старые приглашения и таблица Invitation сохранены, но публичная форма их не требует. Открытая самостоятельная регистрация без обязательного приглашения — последнее продуктовое решение владельца; не возвращать обязательные приглашения без нового решения. Google создаёт нового STUDENT без приглашения, проверяет Google identity и не связывает существующий профиль по одному совпадению email.
- Реальная email-регистрация зависит от RESEND_API_KEY, AUTH_EMAIL_FROM и AUTH_BASE_URL. Без них сервер сообщает о недоступности регистрации; наличие формы не означает доступность операции. Реальный Google OAuth требует GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET и корректный callback URL. В последней проверке части L эти настройки отсутствовали; текущее состояние внешних провайдеров нужно проверять заново без вывода секретов.
- src/lib/login-throttle.ts и src/lib/auth-request-throttle.ts ограничивают попытки в памяти процесса. Прямые запросы не доверяют X-Forwarded-For; доверенный IP возможен только при настроенном proxy. Для публичного многопроцессного размещения нужны общие лимиты на edge/внешнем хранилище.
- Черновик onboarding хранит несекретные поля и шаг в sessionStorage; пароль исключён (src/components/onboarding-wizard.tsx и src/lib/onboarding-draft.ts). Это клиентское восстановление, не серверная гарантия на другом устройстве.

## Резервные копии и ограничения

- buildBackup/restoreBackup в src/server/actions.ts работают с JSON формата 4. Полная owner-копия включает User.passwordHash и другие персональные данные; активные AuthToken, OAuthFlow и неиспользованные приглашения не экспортируются. Не включать такой JSON в TASK-CHANGES.zip и не отправлять его для ревью. Согласованность JSON-снимка при параллельных записях требует отдельной проверки.
- AI, видео и внешние интеграции зависят от настроек и материалов; существование маршрута/кнопки не доказывает работу внешнего сервиса. Контентное покрытие см. CONTENT_COVERAGE.md.
- Старые README.md и DEVELOPMENT_PROGRESS.md содержат исторические состояния. docs/stage01-owner-setup.md обновлён для открытой регистрации и интегрированной основной ветки; фактические настройки внешних провайдеров проверяются отдельно.
- Владелец утвердил дорожную карту этапов 00–09: 00 DONE, 01 IN PROGRESS, этапы 02–09 с отдельными детальными ТЗ перед исполнением. PLAN.md фиксирует её содержание и границы. A01–A06 из D:/НМТ Сайт/architecture/A00-2026-10-20 остаются возможными техническими подпланами, а не заменой утверждённых этапов или доказательством реализации.

## Точки проверки перед изменениями

Для каждого изменения проследить маршрут → компонент → серверное действие → guard → запрос Prisma → личный userId/роль → целевой тест. Перед миграцией или восстановлением рабочей базы требуется отдельное разрешение владельца, согласованная резервная копия, проверка на копии и план остановки/возврата. Полный прогон проверок нужен после миграций, изменений auth/permissions, крупных изменений учебного пути и перед релизом; локальный UI-текст проверяется адресно.
