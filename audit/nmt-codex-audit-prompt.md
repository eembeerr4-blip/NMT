# NMT Academy — правила кодового аудиту для Codex

Це відновлений самодостатній промпт за повідомленням власника від 18.10.2026. Початковий nmt-codex-audit-prompt.md не знайдено, його шлях власнику невідомий. Тому наведені нижче групи й 16 гіпотез не видаються за точну копію відсутнього документа.

## Завдання

Проведи статичний аудит оболонки NMT Academy. Нічого не виправляй, не роби редизайн, не запускай браузер. Оцінюй завершеність шляхів, функціональність контролів, серверні права, власність даних і готовність до наступної перевірки в Chrome. Обсяг навчального контенту та його методичну якість не оцінюй.

## Жорсткі правила

Source read-only; audit-artifacts writable. Створювати файли можна тільки в audit/. Базу, .env, data/secrets.json, вихідні файли, залежності, Git index/конфігурацію та історію не змінювати. Не відкривай й не друкуй секрети. Не зупиняй сторонні процеси чи інші задачі без окремої вказівки власника.

Зафіксуй SHA, branch, git status --porcelain та git worktree list --porcelain. Перевага — уже створений audit-worktree від погодженого SHA. Якщо його немає, можна читати файли commit через git show без зміни робочого дерева. Не коміть стан проєкту й не переносити чужі незакомічені зміни автоматично. Наприкінці порівняй HEAD і tracked diff. Зміни поза audit/ не можна приписувати собі; якщо вони з'явилися, зазнач межу надійності перевірок поточної папки.

Прочитай доступні AGENTS.md. Для Next.js користуйся документацією встановленої версії. Не встановлюй залежності й не запускай postinstall/predev. При потребі нового дозволу поясни конкретну дію; не проси повторних дозволів на вже погоджений аналіз.

## Безпечні команди

Перед npm script прочитай package.json, pre/post hooks, локальні helper scripts і конфіги. Назва команди не доводить безпеку. Заборонено --fix, snapshot updates, migrate/db push/reset/seed/upgrade, dev/start, browser/e2e, записи до робочої БД та setup/teardown із неперевіреними наслідками.

npm test дозволений лише після доказу, що весь вибраний набір не пише БД/файли поза audit/ і не оновлює snapshots. Не створюй тестову базу під час цього аудиту. Якщо цього не доведено, пропусти: «команда не підтверджена як read-only».

npm run build не запускати. Будь-які Prisma-команди, здатні змінювати схему/дані/історію, заборонені. Реальний стан БД за замовчуванням не перевіряти; якщо це окремо необхідно, лише явно read-only з'єднання без PRAGMA-записів, checkpoint, VACUUM або прихованої ініціалізації застосунку.

tsc --noEmit може писати tsbuildinfo при incremental:true. Використовуй прямий локальний компілятор із --noEmit --incremental false, лише після перевірки конфігурації. Lint — без fix і cache. Не імпортуй src/lib/prisma.ts «для читання»: module initialization може запускати WAL PRAGMA.

Чисті функції можна перевіряти синтетичними даними в пам'яті після перевірки всього ланцюга import; harness та результати зберігати тільки в audit/. Не переносити цей дозвіл на DB integration tests.

Якщо виведено секрет, редагуй лише звіт: [REDACTED], не відтворюй значення. Не роби мережеві запити до AI/YouTube й не викликай GET backup: він може писати подію в журнал.

## Точність статичного аналізу

Карти будувати AST-first через вже встановлений TypeScript compiler API/ESLint parser. rg — для орієнтування, не для остаточного висновку. Збережи метод, прогалини резолюції й confidence. Не став «HIGH» лише через відсутність текстового збігу.

Маршрути: src/app, src/pages за наявності, proxy/middleware, config redirects/rewrites, redirect/permanentRedirect/notFound, groups, dynamic/catch-all/optional catch-all, parallel/intercepting. Page URL не містить route groups. Layout guards враховуються для сторінок, але не є захистом HTTP route handlers. Re-export сторінки має фактичну перевірку її реалізації, а не ім'я директорії.

Server Actions: module-level та function-level use server; імпорти й aliases; form action, button formAction, useActionState, startTransition, прямі клієнтські виклики, API/internal/script/test callers. Визначай guard як direct / inherited / indirect / none found / unknown і простежуй фактичний actor → session → role/owner, включно з даними після helper.

«Немає знайденого статичного UI caller» не означає мертвий action. «Немає знайденої вхідної навігації» не означає непотрібна/недосяжна сторінка. Ураховуй redirect targets, callback, deep links і динамічні побудови URL.

Для кнопок перевіряй form owner (також зовнішній form=...), default submit, type, onClick, formAction, onSubmit, requestSubmit, command, href/asChild, router.push/replace та поведінку UI wrapper. Radix Close/Trigger, Tabs і Slot можуть надавати дію дочірній кнопці.

Додатково: form без action/onSubmit може бути повноцінним GET-фільтром поточного URL; перевіряй searchParams. Наявність handler не доводить успішність: перевіряй, чи читається ActionState, чи є pending/error, чи не видаляється чернетка до підтвердження.

Для даних перевіряй і приватні userId-моделі, і записи спільного контенту. Запит по id, отриманому з user-scoped вибірки, не дорівнює IDOR. Запис у спільний контент із дії учня потребує окремої перевірки, навіть якщо модель не має userId.

## Групи аудиту

G1 Авторизація та onboarding; G2 Головна й навігація; G3 Предмети/теми; G4 Урок/відео; G5 Практика/тести/чернетки; G6 Результати/аналітика; G7 Помилки/повторення/картки; G8 План/календар; G9 Конспекти/пошук; G10 Профіль/налаштування; G11 Користувачі/ролі; G12 Контент-адмінка; G13 Backup/журнал/інтеграції; G14 Інфраструктура/БД/продуктивність/дизайн-система/loading/error/empty states.

Для кожної групи: реалізовано в коді; розриви; entry route → component → action → model → permission → наявні тести → майбутня Chrome-перевірка. «Перевірено в браузері» в цьому проході завжди «ні».

## 16 робочих гіпотез

H01 Навігація безпідставно скидає на головну. H02 Ролі захищені лише UI. H03 Учень може отримати повний backup. H04 Editor edit-path існує. H05 Редактор питання зберігає option keys. H06 Авторизація коректна для localhost/LAN/production cookie. H07 Чернетка переживає offline/reload. H08 Таймер обробляє відмову завершення. H09 Завершення атомарне та ідемпотентне. H10 Помилки календарних кнопок показуються. H11 Зміна elective атомарна й зберігає історію. H12 Baseline/goals реально входять до основної гілки. H13 Форми/кнопки без прямого handler є no-op. H14 Guard успадковується й правильно враховує re-export. H15 Student A/B ізольовані та учень не змінює shared metadata. H16 Поточний commit проходить безпечні статичні перевірки.

Для кожної: confirmed / refuted-in-code / partial / requires-runtime, evidence, confidence. Це не замінює невідомих гіпотез старого промпта.

## Результат

Головний файл audit/NMT-code-audit.md. У ньому: SHA і межі; метод; безпечні перевірки й пропуски; групи G1–G14; 16 гіпотез; findings із ID, Priority, Size, Confidence, Evidence, Problem, Trigger, Fix, Acceptance; порівняння feat/personalized-onboarding за окремим SHA; таблиця ownership-кандидатів; Chrome checklist; backlog 6–10 блоків. Посилання файл:рядок мають стосуватися зафіксованого commit. Не вигадуй результатів тестів, HTTP statuses, стану робочої БД та візуальної якості.

Chrome checklist: шість ідентичностей ANON/STUDENT_A/STUDENT_B/EDITOR/ADMIN/OWNER, роль × маршрут × стан × viewport × очікування. Мінімум 1440×900 та 390px; порожні/заповнені/помилкові/завантаження/відмова доступу, refresh/back/forward, Dark Reader вимкнений. Потрібні screenshot, фактичний URL, console errors, network statuses без токенів. Поточний аудит лише готує цей список, не створює акаунти й не виконує мутації.

Окремо END-TO-END STUDENT PATH: реєстрація → onboarding → elective → baseline/skip → goals → головна → предмет → тема → урок → практика → тест → результат → помилки → повторення → календар → прогрес → вихід → вхід → продовження. Познач, які етапи ще потребують інтеграції гілки.

Наприкінці перевір HEAD, git status і diff: жодних змін коду/даних. Не коміть звіт автоматично. Виправлення та браузер — окремий наступний етап після цього звіту.
