# NMT Academy: фактическое состояние и план оставшихся работ

Дата проверки: 19 октября 2026 года.

## 1. Вывод для владельца и следующего ИИ

NMT Academy уже является работающим приложением на Next.js, React, TypeScript, Prisma и SQLite. Переписывать его на Flask/Express, заново создавать авторизацию, роли или админку не требуется. Приложенный общий план не учитывает значительную часть существующего кода.

Главная организационная проблема: исходный проект, опубликованная версия и отдельная визуальная бета находятся на разных ветках. Самая заметная новая функция из приложенного задания — полноценная загрузка файлов материалов. Сейчас есть текстовый редактор урока, источники-ссылки, YouTube и банк вопросов, но нет общего файлового хранилища с метаданными и защищённым получением файлов.

Следующий шаг: выбрать основу дальнейшей разработки, проверить и перенести уже готовую бету по отдельному разрешению владельца, затем реализовать файлы и завершить оставшиеся сценарии. Начинать всё с нуля или вслепую объединять ветки нельзя.

Это проверка кода и планирование. Код, схема, миграции, рабочая база, учебные материалы и удалённые ветки в этом проходе не изменялись. Создан только этот отчёт.

## 6. Порядок работ: независимые блоки

Размеры S/M/L — относительная сложность, не обещание времени или расхода квоты.

### B00 — выбрать и зафиксировать основу (P1, S)

- Сохранить SHA всех рабочих веток и рабочие деревья.
- Показать владельцу отличие опубликованной версии от беты, получить решение об интеграции. Слияние без разрешения не выполнять.
- Если выбрана бета: проверить её diff и переносить существующие исправления; старую onboarding-ветку не объединять целиком.
- Уточнить имя будущей основной GitHub-ветки отдельно от выбора кода.
- До изменения целевой базы проверить её фактический статус миграций. В репозитории пять миграций; их наличие не доказывает применение.

Готовность: одна согласованная исходная версия, записанный SHA, воспроизводимые QA-команды, исходные ветки/данные сохранены.

### B01 — зафиксировать права и управление пользователями (P1, S)

- Сохранить существующую иерархию OWNER/ADMIN/EDITOR/STUDENT и текущие ограничения.
- Проверить поиск по нику, подтверждения, выдачу/снятие роли, обновление экрана, запись журнала.
- Проверить прямые серверные вызовы после понижения роли, истечения сессии и от другого пользователя.
- Не создавать новые таблицы roles/user_roles без требования нескольких ролей одновременно: текущему продукту достаточно существующей модели.

Готовность: OWNER назначает ADMIN/OWNER другому профилю; ADMIN не повышает до ADMIN/OWNER; EDITOR/STUDENT не меняют роли; отказ AuditLog откатывает изменение. Проверить оба viewport 1440×900 и 390×844.

### B02 — завершить надёжную регистрацию (P1, M)

- Профиль, настройки и предметы финализируются атомарно; признак завершения не появляется раньше данных.
- Повторная отправка/две вкладки не создают дубликаты, отказ не оставляет «готовый» сломанный профиль.
- Подтверждённые шаги можно возобновить после обновления и входа.
- Расширенные baseline/цели по предметам не включать автоматически: это отдельный B08.

Готовность: тесты отказа и повторной отправки; в Chrome новый ученик проходит путь и продолжает незавершённый профиль. Рабочую базу при разработке не использовать.

### B03 — файловая CMS и хранение метаданных (P1 по заданию, L)

Предлагаемый минимальный объём для согласования перед реализацией:

- Первая версия: PDF, JPEG, PNG, WebP как вложения темы. Текст урока остаётся в существующем редакторе, видео — по текущим YouTube-ссылкам. Собственная загрузка видео — отдельное решение по объёмам и инфраструктуре.
- Форма: файл, название, описание, тема, статус черновик/опубликован/архив. Ясные сообщения об ограничениях, ошибке и успешном сохранении.
- Модель метаданных: ID, topicId, storageKey, исходное имя, MIME, размер, контрольная сумма, создатель, статус, даты. Метаданные в БД, содержимое вне `public/` и вне Git.
- Файлы на локальном постоянном диске для локального/VPS-развёртывания; для среды без постоянного диска нужен отдельный адаптер объектного хранилища. Не покупать сервисы и не менять хостинг без решения владельца.
- Разрешённые типы и предельный размер проверяются сервером по содержимому и расширению. Имя хранилища генерируется сервером; пользователь не передаёт путь. Исполняемые форматы и HTML/SVG не входят в первую версию.
- EDITOR/ADMIN/OWNER загружают и редактируют; STUDENT читает разрешённые опубликованные материалы. Получение файла проверяет сессию/статус на сервере; угадывание URL не даёт доступ к черновику.
- Согласовать правило доступа по предметам, прежде чем считать просмотр общей библиотеки ошибкой. Не добавлять незаказанные платные уровни доступа.
- Продумать частичные отказы файловой системы, БД и журнала: не объявлять успех без файла; не оставлять доступный незарегистрированный файл. У БД и файловой системы нет общей транзакции — нужна явная последовательность и компенсация/сверка.
- Архивирование и замена сохраняют нужную историю; первоначально не выполнять безвозвратное удаление.
- Новую миграцию сначала проверить на пустой QA-базе и QA-копии. Применение к рабочей базе — отдельный выпуск с резервной копией и подтверждением.

Готовность: файл загружается, сохраняется после перезапуска, имеет метаданные и событие журнала; ученик открывает опубликованное вложение темы; чужая роль, черновик, неверный формат, превышение лимита, подмена имени, отсутствие файла и отказ хранилища обработаны тестами и понятными сообщениями.

### B04 — публикация контента и путь ученика (P1, M)

- Использовать существующие редакторы тем/уроков/вопросов.
- Проверить/принять готовые функции наборов из беты: preview, черновик, публикация, архив, новая версия без разрушения попыток.
- Добавить вложения B03 в урок и список материалов с корректными пустыми состояниями.
- Сетевой отказ не теряет введённые данные; повторное нажатие не создаёт дубль.
- Отсутствие видео или файлов не блокирует имеющуюся теорию. Не показывать обещание работающего действия, если нужного материала нет.

Готовность: редактор готовит материал → публикует → STUDENT видит его → проходит урок и практику → получает результат → возвращается после входа с сохранённым состоянием. Неизменяемая история старых попыток сохранена.

### B05 — backup/restore, включая новые файлы (P1, M)

- Согласованный JSON snapshot и тест параллельных записей.
- Разделение безопасного обезличенного экспорта и полного приватного восстановления с учётными данными.
- Полный backup включает метаданные и сами вложения либо документированный согласованный архив хранилища; одного JSON с путями недостаточно.
- Проверка восстановления в новый каталог/базу: записи, связи, контрольные суммы файлов, integrity/foreign keys и повторный вход.
- При WAL использовать согласованный способ SQLite backup, а не слепую копию одного файла с игнорированием WAL.

Готовность: отдельная восстановленная QA-копия полностью пригодна для обучения; рабочий экземпляр не заменялся в тесте.

### B06 — условия публичного запуска (P1 до внешнего доступа, M)

- Ограничитель входов по IP/аккаунту, политика регистрации, безопасная первичная инициализация owner.
- HTTPS и корректные cookie, секреты только в конфигурации сервера.
- CI для проверок, изолированная QA-БД, production build в отдельном окружении.
- Постоянное хранение БД и вложений, резервное копирование, наблюдение за ошибками и место на диске, инструкция выпуска/отката.
- GitHub хранит код. Учебные результаты, секреты, приватные backup и локальные QA-артефакты туда не загружать.

Готовность: проверенный внешний тестовый экземпляр с восстановлением и ролями. Для исключительно локального использования этот блок можно отложить; не выдавать локальную бету за публичный релиз.

### B07 — итоговая приёмка оболочки (P1, M)
